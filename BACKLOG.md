## Design debt

- [x] **`HASH_MIN_PROPS = 8` is correct; hashing small objects unconditionally is a large regression** — measured, because three separate profiles pointed here and the lead is wrong. The theory was that small objects and prototype chains pay for `find_prop_idx` walking the shape chain (`src/hobject.c3:1169`, one `shape_extend` node per property) where QuickJS's `find_own_property` hashes unconditionally off the shape. Setting `HASH_MIN_PROPS = 1` and rebuilding measured **+19.59% on `bench_object` and +17.83% on `bench_memory_heavy`** (retired instructions), while `bench_property_lookup` moved **+0.01%** and `bench_ic_proto` +0.02%. The per-object hash table costs an allocation and a build that few-property objects never amortize, and the zero movement on the two lookup benchmarks shows the inline caches already absorb those lookups — `find_prop_idx` is barely on their hot path. Do not lower the threshold, and do not attribute the `object`/`property_lookup` gap to the shape-chain walk. Still current: the constant is `HASH_MIN_PROPS = 8` (`src/hobject.c3:75`) and the hash table still builds only past it (`:994`, `:1476`); the recorded measurement is the standing evidence, no follow-up is open
- [x] **A cached `prop_values()` slot pointer must be guarded on `prop_alloc`, NOT on the shape generation** — recorded because the obvious guard is the wrong one and a perf attempt already reached for it. `HObject.grow_array` (`src/hobject.c3:1744`) reallocs `prop_alloc` — the dense array part shares the block, sitting after the property values — while leaving `shape_id` unchanged and never calling `bump_shape_gen`. So a shape-generation guard misses that move entirely and a cached slot pointer becomes a use-after-free. The correct guard is the `cached_prop_alloc` pointer compare that `ICEntry` already uses. There are exactly four writers of `prop_alloc`: `grow_props`, `grow_array`, object creation and object free. ABA is closed because `bindings` is a strong GC root through the cache (`src/heap.c3:2832`), so an object cannot be freed and its address reused under a live entry. Still current: `grow_array` (`src/hobject.c3:1755-1780`) reallocs `prop_alloc` (`:1772`) with no `bump_shape_gen`, and both cache entry types (`ICEntry` `:2325`, `MegamorphicEntry` `:2381`) compare `cached_prop_alloc` against `owner.prop_values()` on every hit (`:2404`, `:2426`). Recorded as a do-not-regress note; the guard is in place

Reproducer: build a 400-char string with `s += ...`, then `JSON.parse(JSON.stringify({[s]: 1}))[s]` yields `undefined` where qjs yields `1`. `o[s]`, `in`, `hasOwnProperty`, `Map`/`Set`, `Object.keys`, `===`, `indexOf` and sort all go through the interning path and are correct — the leak is narrower than it first looked, but it is a silent wrong-answer class, so the fix is to find the missing force-intern sites rather than patch JSON alone. Predates the string-hashing work (`3380bc85`) and is unaffected by it. Fixed by `8af395d6` (see the long-string identity entry): `put_prop` interns on store so no stored key is ever un-interned, `builtin_to_property_key_vm` interns on the builtin lookup path (an audit found exactly one further hand-rolled coercion, `Object.getOwnPropertyDescriptor`, now routed through the shared helper; the `vm_property.c3` poison-pill check is provably safe since `"caller"`/`"arguments"` are always short enough to intern), and JSON.parse interns each key it records so reviver bookkeeping matches the canonical stored key. Differential against qjs on the reproducer and the 255/256/257 boundary: identical

- [x] **`StrBuf` by-value copy hazard documented** — `data` points into the struct's own `inline_buf` until the first growth, so copying by value dangles the copy's pointer. Silent and size-dependent: corrupts buffers <= 256 bytes, looks correct for grown ones. Audited the tree: `src/builtins/inspect.c3:862` is the ONLY by-value copy and it already re-points `data`; no other site copies one. A do-not-copy warning now sits on the struct definition (`src/builtins/core.c3`) so a future copy does not reintroduce it silently

- [x] **The last hand-rolled copy of the `await` identifier predicate is gone** — `shorthand_key_is_identifier_ref` in `src/compiler/destructuring.c3` now calls the shared `await_is_identifier`. Folded into the arrow-parameter fix, since that work routed the scan and binding sites through the same helper. This pattern, one invariant hand-maintained at N sites and wrong in the copies that omit it, was the root cause six times (the four session-302 codegen bugs, plans 063/064/065/066); four of those fixes worked by *removing* copies

- [x] **Compile-error state raced across threads** — `g_last_err_msg/_line/_col` were process globals written by every parser fault path and read by every compile caller. The documented concurrency model is one runtime per thread in parallel (the Rust example spawns three), so two threads compiling failing code at the same time tore the shared 512-byte buffer: a thread read the other's message, a splice of both, or an empty one, and a `finish()`-level stale-message check could fail the next valid compile (the old `entry.c3:317` poisoning comment). The error state now lives on the caller's `Lexer` (`err_msg/err_line/err_col`), the per-compilation owner every writer already had in scope (`self.lexer`), and the top-level entries reset it per compile. All ten reader sites (C API, C3 binding, module loader, both CLIs, test262 runner, capi tests) read from their own lexer; the module-level buffer and `last_error_msg()` accessors are gone. `test/capi/compile_threads.c` (`make test-compile-threads`) runs four threads × 20k iterations of failing+valid compiles with a per-thread offending byte in the source; each thread must see exactly its own message. Against the pre-fix tree the test fails loudly (150/20000 wrong messages and poisoned valid compiles); with the fix it is deterministic-pass
- [x] **Some parse faults reported an empty SyntaxError** — a survey of ~3,000 invalid programs found ~20 grammar paths that `return COMPILE_ERROR` without recording a message, so the CLI printed `SyntaxError:  (line 0, col 0)` for common typos (`var ] x`, `class {`, `x.`, `new .`, `let {`, `var x = {`, `x.#x` undeclared, bare `super`, `class C { *`). The C API masked these with a "SyntaxError" fallback; the CLIs did not. Every surveyed path now records a message (binding-identifier, class-name, property-name, destructuring-key, object-literal-key, method-or-field-name, super-context, private-name, new.target). `test/compile_error_messages/run.sh` (wired into `test-local`) pins the previously-empty cases; a 2,904-case generated battery now reports zero empty messages
- [ ] **`g_private_class_id` is a benign data race** — the compiler's last process-global mutable state is the monotonic id handed to each class body for private-slot binding names (`src/compiler/private_names.c3:28`). Two threads compiling classes concurrently can both read the same value, so two classes in *different runtimes* share an id. This is behaviorally inert: the slot names are interned per-heap and the environments they live in are per-runtime, so a duplicate id across heaps never collides, and within one thread the counter is monotonic. Fixing it properly needs an atomic or a mutex (C3 0.8.2 has no stdlib atomics) and moving it into `CompilerContext` is unsound: an arrow shares its parent's env, so sibling classes compiled by different nested contexts (parent vs arrow) must not restart the counter (verified: `class A {#x}` inside a function plus `class B {#x}` inside an arrow in the same function must get distinct ids). Left global and documented rather than churned
