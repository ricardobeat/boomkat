## Core language bugs

- [x] **Property writes silently fail once the shape table is exhausted.** After ~65k unique property-key transitions *process-wide*, `o[k] = v` reports success and `o[k]` immediately reads back the wrong value, with no error. Plain JS reproducer on `./out/duktape_c3`: `var o={}; for (var i=0;i<70000;i++){ var k="k"+i; o[k]=i; if (o[k]!==i) break; }` → misses at **65535**. Root cause: `Shape.shape_id` is a `ushort`, so `Heap.alloc_shape_slot` (heap.c3:1112) returns `SHAPE_NONE` past 65534; both call sites (hobject.c3:1143 and :1577) then `shape_free` the new shape and keep the old one, so `put_prop` writes the value and returns `true` while the shape never records the key — `find_prop_idx` returns -1 right after a "successful" store, and `delete_prop` can never find it. The budget is **global, not per object**: two objects with distinct 40k key sets fail at iteration 0 of the second, while two objects sharing a transition chain are fine. `Map` is unaffected and is the workaround for large dynamic key sets. Should fail loudly (throw) rather than corrupt silently, even if the 16-bit id stays. Found while stress-testing the Rust binding; pre-existing, not caused by host functions. Verified fixed on current main: the 70k-key loop runs to completion.

- [x] **Arrow parameters clobbered by a void-context call in the body, eval path only.** `((x)=>{Math.max(1,2); return x+100})(7)` yields **102 instead of 107**, and `((x,y)=>{Math.max(1,2); return x+y})(3,4)` yields 6 instead of 7. ## Latent runtime bugs

- [ ] **Strings over `MAX_INTERN_BYTES` compare unequal in `Map`, `Set`, `includes`, `Object.is` and JSON round-trips** — such strings are deliberately left un-interned, and `same_value_impl` (`src/builtins/map.c3:16`) compares the STRING case with a bare `a.get_heapptr() == b.get_heapptr()`, while `HObject.find_prop_idx` (`src/hobject.c3:1219`) matches keys with a bare `e.key == key`. Neither has the content fallback `equals_hstring` gives `===`. Building the same 330-char string twice and using it as a `Map` key returns `undefined`, `Set.has` and `Array.prototype.includes` return `false`, `Object.is` returns `false`, and a `JSON.parse(JSON.stringify(o))` of such a key reads back `undefined`; QuickJS is correct on all six. `===`, `indexOf` and `switch` are unaffected because they route through `equals_hstring`. `get_prop_key` calls `Heap.ensure_interned` and is its only caller, which is why direct `o[big]` access works and the collection paths do not. This is the reason interning cannot simply be deferred for value-like strings to cut intern cost: the identity surface is wider than the fallback. Either give `same_value_impl` and `find_prop_idx` a content fallback for the non-interned case, or intern at those boundaries the way `get_prop_key` does

- [x] **A warmed variable IC serves a stale value after `eval` redeclares the global** — `var g1=1; function r(){return g1}; r();r();r(); eval("var g1 = 2;"); r()` returns `1`; node returns `2`. Not a bug: the engine is strict-only, so a direct eval is always strict and its `var` declarations are confined to the eval's fresh declarative environment (ES2015 §18.2.1.1 step 18.f; `src/builtins/global.c3:1006`). A strict-mode node reproducer returns `1` as well; the entry compared against sloppy node, whose eval `var` leaks by design. Assignment through eval (`eval("g1 = 2")`) does write through to the outer binding, and that path works. No IC staleness involved, the eval body never touches the warmed slot. Verified on `main`: direct read, warmed read, and a fresh function all see the unchanged `1`, matching strict node on global and function scope

- [x] **`test262_runner --worker` segfaults on `staging/sm/class/superPropProxies.js`** — exit 139, reproducible on clean `main` with that one path as the whole input, so it needs no preceding test and is not batch-state dependent. The same source runs clean under `./out/duktape_c3` with the harness concatenated, which puts the fault on the runner path rather than the language. Invisible to the gate because `staging` is skip-listed, so this is out of the targeted subset; it is recorded because a segfault in a shipped entry point is worth understanding regardless of which corpus surfaced it. The test combines `class mid extends new Proxy(base, handler)` with `super` property get/set through a proxy on the prototype chain; neither construct crashes on its own. Verified fixed on current main: the test now fails cleanly with `createRealm not supported`, the out-of-scope cross-realm path, and the worker exits 0.

- [x] **`test/test_async_loops.js` segfaulted under aggressive GC** — a generator/async resume restores `gs.saved_regs` with `tval_copy_ref`, taking a reference per heap value, but bypassed `track_heap_store` while `activation_begin` had just reset `max_heap_reg = 0`. `decref_callee_regs` sweeps only `[0..max_heap_reg]`, so restored registers above the highest index the resumed body happened to rewrite were never decref'd or cleared: the reference leaked and the slot kept stale pointer bits, which `vm_mark_activations` later read through a different frame reusing that valstack address. `track_restored_regs` raises the watermark over the restored window at both resume sites. Reachable in principle at any GC cadence; it needed collection pressure to surface. `just test-gc-stress` now covers it
- [x] **The `max_heap_reg` sentinel collision is gone** — the field stored the highest register index holding a heap reference, so the empty case and register 0 were both 0 and `decref_callee_regs`' early-out could not distinguish them. No shape reached it (arguments in register 0 are borrowed; a value returned out of register 0 is tracked on the caller), but both are ownership rules rather than guarantees. Replaced by `heap_reg_count`, one past the highest such index, so register 0 is expressible. Two writers, one reader and four resets moved together
## Design debt

- [ ] **A cached `prop_values()` slot pointer must be guarded on `prop_alloc`, NOT on the shape generation** — recorded because the obvious guard is the wrong one and a perf attempt already reached for it. `HObject.grow_array` (`src/hobject.c3:1744`) reallocs `prop_alloc` — the dense array part shares the block, sitting after the property values — while leaving `shape_id` unchanged and never calling `bump_shape_gen`. So a shape-generation guard misses that move entirely and a cached slot pointer becomes a use-after-free. The correct guard is the `cached_prop_alloc` pointer compare that `ICEntry` already uses. There are exactly four writers of `prop_alloc`: `grow_props`, `grow_array`, object creation and object free. ABA is closed because `bindings` is a strong GC root through the cache (`src/heap.c3:2832`), so an object cannot be freed and its address reused under a live entry
- [ ] **Four VarIC fill sites set `shape_id` without setting `recycle_epoch`** — `src/vm/vm_arith.c3:552` and `src/vm/vm_execute.c3:4091`/`:4333`/`:4514` populate an entry and leave `recycle_epoch` holding whatever the slot last had, while other read paths on the same array (`vm_arith.c3:227`, `vm_execute.c3:3781`) do compare it. Not currently reachable: those reads also require `vic.key` to match, and these fill sites never set `key`, so their entries cannot satisfy the epoch-checking readers. That makes it latent rather than live — but it is one added `key` write away from becoming a stale-cache wrong answer, which is exactly the class that made `n_queens.js` silently miscount before `23901323`. Route every fill through one helper that populates all guard fields together

- [ ] **A generational nursery would not help; the allocation-heavy gap is dispatch, not GC** — measured rather than assumed, so future perf work does not re-derive it. Instrumented collection counts: `bench_object` runs **1** collection in its entire life (499 objects visited, 504 allocations) and is still ~1.55x qjs, so no young-generation scheme can move it by construction. `bench_memory_heavy` runs 9; a 3M-object allocation microbenchmark averages ~1.5 heap-list nodes visited per allocation, and the `gc_trigger_counter` rescaling (`src/heap.c3:3411`) is already amortized O(1). QuickJS is likewise refcount + cycle collector with **no nursery**, so the strategy is not the differentiator. Profiles put `bench_object`'s cost in `Vm.run` dispatch, `dispatch_property` and `th_getglobal` — with no GC and no allocator in the top entries at all. The remaining lead worth trying is `find_prop_idx` only hashing above `HASH_MIN_PROPS = 8`, so small objects walk a shape chain that `shape_extend` builds one node per property, where QuickJS's `find_own_property` hashes unconditionally off the shape. An `append_known_absent` extraction that removed the duplicate scan measured ~2% on a pure-allocation microbenchmark and within noise on the named benchmarks, so it was not merged

- [ ] **`ensure_valstack` is called with an absolute slot index but documents a relative count** — the contract is "room for `needed` MORE slots" and the check is `valstack_top + needed <= valstack_end` (`src/vm/vm_coerce.c3:172`), but the call-setup sites compute `needed` as an absolute index from the stack base: `(uint)(new_bottom - vm.valstack) + target.num_regs` (`src/vm/vm_calls.c3:768`, `:1701`, `:1937`, `:2550`). Since `new_bottom >= vm.valstack`, the argument is always >= the true requirement, so this errs toward over-reserving and is safe today — but the valstack grows earlier and larger than intended, and the two readings diverge further the deeper the frame. Fix by passing the relative count (or by changing the parameter to an absolute watermark and updating the comparison), not by adjusting one call site. Found while profiling the call path; unrelated to the fast-path work in `12423867`

- [ ] **A non-interned string key reaches builtins that compare by pointer identity** — string equality is pointer identity engine-wide, but strings over `MAX_INTERN_BYTES` (256) are deliberately left un-interned and re-interned on demand by `Heap.ensure_interned`. That helper has exactly ONE caller, `get_prop_key` in `src/vm/vm_coerce.c3:246`, so any builtin that reaches a string key by another route compares a non-interned pointer and misses. Reproducer: build a 400-char string with `s += ...`, then `JSON.parse(JSON.stringify({[s]: 1}))[s]` yields `undefined` where qjs yields `1`. `o[s]`, `in`, `hasOwnProperty`, `Map`/`Set`, `Object.keys`, `===`, `indexOf` and sort all go through the interning path and are correct — the leak is narrower than it first looked, but it is a silent wrong-answer class, so the fix is to find the missing force-intern sites rather than patch JSON alone. Predates the string-hashing work (`3380bc85`) and is unaffected by it

- [x] **`StrBuf` by-value copy hazard documented** — `data` points into the struct's own `inline_buf` until the first growth, so copying by value dangles the copy's pointer. Silent and size-dependent: corrupts buffers <= 256 bytes, looks correct for grown ones. Audited the tree: `src/builtins/inspect.c3:862` is the ONLY by-value copy and it already re-points `data`; no other site copies one. A do-not-copy warning now sits on the struct definition (`src/builtins/core.c3`) so a future copy does not reintroduce it silently

- [x] **The last hand-rolled copy of the `await` identifier predicate is gone** — `shorthand_key_is_identifier_ref` in `src/compiler/destructuring.c3` now calls the shared `await_is_identifier`. Folded into the arrow-parameter fix, since that work routed the scan and binding sites through the same helper. This pattern, one invariant hand-maintained at N sites and wrong in the copies that omit it, was the root cause six times (the four session-302 codegen bugs, plans 063/064/065/066); four of those fixes worked by *removing* copies
