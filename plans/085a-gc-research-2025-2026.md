# GC and allocator research: January 2025–19 September 2026

Research companion to [085 — EnvRecord reclamation](085-envrecord-reclamation.md). Findings below distinguish released implementations from experiments; applicability judgments are recommendations for Boomkat, not performance claims about this engine.

## Findings from primary sources

| Development | Evidence and dates | What Boomkat can use |
|---|---|---|
| **Go Green Tea GC** | Experimental in Go 1.25; design article 2025-10-29; default in Go 1.26, released 2026-02-10. Uses page-local marking/scanning state and page-oriented work scheduling to improve locality. Go reports roughly 10–40% lower GC overhead for relevant GC-heavy workloads, not equivalent whole-program speedups. [Design](https://go.dev/blog/greenteagc), [Go 1.26](https://go.dev/blog/go1.26), [release notes](https://go.dev/doc/go1.26). | Later, compare page/block-local work queues with pointer-by-pointer marking. EnvRecord's fixed-size pool already provides a useful locality unit. First establish exact roots and first-visit marking; do not transplant Go's concurrent machinery or hardware-specific optimizations. |
| **Ruby 4.0 GC improvements** | Released 2025-12-25. Independent growth of size pools, improved large-object-page sweeping, and lazy identity metadata allocation reduce unnecessary space/work. [Release announcement](https://www.ruby-lang.org/en/news/2025/12/25/ruby-4-0-0-released/). | Account for environment pressure independently, return empty blocks, and keep optional diagnostics out of each cell. Retain full-heap mark cost in scheduling so one small allocation category does not trigger excessive full collections. |
| **CRuby/MMTk memory-management work** | ISMM 2025 paper, 2025-06-17; author article 2025-09-16. Explores GC integration, precise object identification, pinning, and more explicit pointer descriptions. Advanced MMTk integration is experimental, not a claim that stock Ruby ships every described collector. Ruby's modular-GC foundation predates this window in Ruby 3.4. [Paper](https://railsatscale.com/2025-09-16-reworking-memory-management-in-cruby/paper.pdf), [author article](https://railsatscale.com/2025-09-16-reworking-memory-management-in-cruby/). | Maintain a complete root/field inventory and debug allocated-cell validation. Separate liveness from pinning concepts. Boomkat's temporary roots must trace children; movement pinning in another runtime is not the same contract. |
| **Zig 0.14 allocator changes** | Released 2025-03-05. `DebugAllocator` succeeds `GeneralPurposeAllocator`; `SmpAllocator` addresses fast multithreaded allocation, including reuse associated with exited threads. Zig has no automatic language garbage collector. [Release notes](https://ziglang.org/download/0.14.0/release-notes.html), [release index](https://ziglang.org/download/index.json). | Separate diagnostic allocator costs from release allocation costs. Keep the single-threaded EnvRecord freelist simple; thread caches and synchronization would add machinery without solving scope reachability. |
| **Zig 0.16 memory APIs** | Release archive dated 2026-04-13; announcement 2026-04-14. Includes thread-safe lock-free arena work and unmanaged memory-pool API changes. [Release notes](https://ziglang.org/download/0.16.0/release-notes.html), [announcements](https://ziglang.org/news/), [memory model](https://ziglang.org/documentation/master/#Memory). | Explicit allocator ownership is useful for embedding and measurement. A frame arena alone cannot reclaim escaping scopes safely; their lifetimes overlap and are not stack-shaped. |
| **SILB-Recycler / `rust-cc`** | SAC 2025, March 31–April 4. Single-threaded reference-count cycle collection using intrusive traversal and avoiding supplementary collection allocation. [Paper](https://saveriogiallorenzo.com/publications/sac2025a/sac2025a.pdf), [implementation](https://github.com/frengor/rust-cc). | Useful evidence for iterative bounded-stack traversal. Its cycle algorithm requires a counted-edge model that Boomkat's environment/register graph does not have. Adopting it would require an ownership redesign, not a small fix for pool retention. |
| **PyPy allocation sampling** | Paper submitted 2025-06-20 describes sampling-based allocation profiling and tunable profiling costs. [Paper](https://arxiv.org/abs/2506.16883). | Start with aggregate environment allocation/liveness counters. If attribution is still unclear, add optional sampled allocation-site statistics rather than recording every allocation in production. |
| **Go 1.27 allocation specialization** | Released 2026-08-19. Specialized small-allocation paths trade some binary size for lower allocation overhead; published improvements concern particular allocation costs/workloads, not a universal runtime speedup. [Announcement](https://go.dev/blog/go1.27), [release notes](https://go.dev/doc/go1.27). | EnvRecord already has one fixed cell size and a dedicated freelist. Preserve that advantage; avoid introducing a general allocator abstraction or code-size growth on the hot path without measurements. |

## Recommended order

1. **Apply now:** exact mixed object/environment tracing, an allocated-state verifier, explicit temporary-root rules, iterative first-visit traversal, weak variable caches, empty-block release, and allocation-pressure/counter instrumentation.
2. **Measure next:** mark locality and pool fragmentation. Green Tea's page-oriented processing is a plausible follow-up if profiles show pointer chasing dominates. Keep the optimization independent of correctness.
3. **Investigate only with evidence:** sampled site attribution, more compact capture layouts, or additional allocation specialization.

Moving/concurrent collectors, generational barriers, and RC trial deletion are substantial architectural changes. None is necessary to reclaim EnvRecord cells correctly. The immediate design uses the existing synchronous non-moving collector and preserves current counted-edge contracts.

Report allocator-reserved bytes and live cells alongside RSS. Returning an empty block to the allocator is an engine action; the allocator returning its pages to the operating system is a separate action. This distinction matters particularly on small devices and when comparing allocators.

This is a targeted research survey, not an exhaustive list of every collector released in the period. No performance improvement from another runtime is assumed to transfer without a Boomkat benchmark.
