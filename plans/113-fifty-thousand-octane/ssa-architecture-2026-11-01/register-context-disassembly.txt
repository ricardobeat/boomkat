Target-derived embedded SSA scratch context, 2026-11-01

Shared API: jit::scratch_register_count(int saveds). Production count is
SLJIT_NUMBER_OF_REGISTERS minus the fixed saved-register count. Function bodies,
native call entries, link fallbacks and inherited resume fragments all request
scratch_register_count(6), six FPR scratches and six saved GPRs. The C ABI
gateway remains3/3. Parent SSA configuration exposes scratches−4 homes only
for embedded direct-field SSA; the R6-state path retains two contiguous homes.

ARM64:26 total−6 saved=20 scratch, so embedded direct-field GPR homes expand
from R4..R6 to R4..R19. x86-64:13−6=7 scratch, unchanged. SLJIT allocates the
extra ARM64 scratch registers from ABI-preserved x25..x28, preserving them in
the generated prologue/epilogue. Scratch and saved logical register sets remain
disjoint. No home-indexed7/3-sized allocator arrays exist; home is an integer
and allocator loops use the graph's target budget. All current embedded SSA
calls pass direct=true; parent also fixes inherited graph saveds explicitly6.

Control feature SLJIT_NO_EXTRA_FUNCTION_SCRATCH caps the derived count at7
for a matched build. Candidate/control diagnostics use SLJIT_STATS+SLJIT_MAP
in addition to normal boomkat project features. No timing claim is made.

The expanded context adds two save instructions to each internal entry and
matching restore instructions to each return, growing the whole owner despite
leaf savings because baseline exits each emit unwind code. This is a measured
code-generation tradeoff; matched throughput/full-suite results must decide
the production default. Runtime helpers materialize state before leaving SSA;
no expanded SSA home is assumed live across a native helper/callee call.
