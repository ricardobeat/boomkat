# Capture and widened dispatch experiments — rejected

On rat `c74029b2`, the prior zlib sample attributed substantial time to `capture_read_slot`, called from `th_getcap`. ARM64 disassembly (`bk-getcap-control.asm`) shows the handler saving callee-saved registers and calling the helper; adding `@inline` removes that call and frame (`bk-getcap-candidate.asm`). Five alternating mini pairs nevertheless gave zlib 3720→3719 ms, with crypto, Gameboy, Mandreel, TypeScript and DeltaBlue essentially neutral. Inlining alone was removed.

An OP_PROFILE build of the current zlib mini recorded 78,584,077 GETCAP executions and 58,606,941 GETCAP→SHRI pairs. The initial fusion assumed the shift consumed the capture's destination and did not trigger. Inspecting actual bytecode in `bk-capture-shift-bytecode.log` showed the important case: the capture supplies an array and the shift computes a separate index. A revised guarded fusion published the capture and then applied the shift using its own operands. The profiling build confirmed 58,606,941 additional fused bytecodes, while preserving the total 792,969,345 executed bytecodes. However five uninstrumented pairs were 3707→3730 ms for zlib (+0.62%). The instrumented runtime fell 10862→10423 ms but that is not a valid release-performance comparison. The fusion was removed.

A separate fast publication path for inert values or already-publishable objects was tested with inlining. Five pairs gave zlib 3727→3709 ms; a fresh seven-pair confirmation gave 3717→3724 ms. Other screened minis were essentially neutral. The path and inline annotation were removed. The JS fixture in this directory passed on both builds and Node, but these experimental variants did not receive full release or full Octane gates.

A follow-up instrumentation broke down `th_wide` payloads: 292,039,444 handler entries, including 89,042,104 LDINT, 53,103,758 LDREG, 33,692,334 BOR and 23,727,696 ADD. These are handler-entry counts, including retries and distinct from the OP_PROFILE dynamic WIDE count. The control ARM64 handler decodes several fields and goes through a general opcode decision tree before the integer-load path (`bk-wide-control.asm`). A variant that checks LDINT and LDREG earlier shortened the LDINT path (`bk-wide-fast.asm`) but five release pairs regressed zlib 3702→3756 ms (+1.46%). Isolating the LDINT early check regressed 3715→3793 ms (+2.10%). Both variants were removed; their mini results and the last patch are retained here.

These results show that eliminating dispatches or static instructions in isolation is not enough for these paths. The next JIT work still needs a decoded widened region with a recovery-aware register representation and substantially better code quality. The 50K full-Octane objective is not met.

The actual dynamically evaluated zlib source was extracted and compiled with the trace build. The attempted `a1` function region begins at PC 31045, a WIDE prefix: the listing in `a1-region-31045-bytecode.txt` shows widened LDINT/BOR/EQ/conditional branches involving r484–r486, then widened GETVAR, GETPROP and PUTPROP. The final profile reports `a1` at 300,053,634 threaded and 36,553,493 switch bytecodes, with this region rejected as WIDE. Existing loop plans install but account for few completed iterations in that run. A correct function-tier solution must translate widened operands to actual frame registers and retain the original prefix PC for every guard, branch target and resume; the existing low-slot loop remap cannot be applied to the function tier without also mapping frame loads/stores, call windows and recovery. This explains why adding a WIDE check or reusing the loop alias table is not a sufficient implementation.
