# The two-tier JIT

The JIT compiles JavaScript to native code in two tiers that share the
interpreter's frame layout: an optimized body can leave for the baseline code
of the same frame and continue there, and a baseline frame can enter optimized
code in the middle of a loop.

Both tiers are off by default. See [build-flags.md](build-flags.md#jit) for the
build settings and [embedding.md](embedding.md#native-compilation) for the C
API switches.

## Baseline tier

`--jit` enables it. It compiles each eligible function the first time its entry
count passes `OPT_ENTRY_THRESHOLD` (1000 calls; a back edge counts a quarter),
either on function entry or, for a hot loop, at the back edge itself.

The baseline emitter covers every opcode outside its exclusion list. Its fast
paths are numeric, compare-and-branch, and property access through the same
inline caches the interpreter fills; everything else runs the shared operation
functions. Code is emitted lazily, so a compiled function that never throws
carries no throwing path. An instruction the emitter cannot handle leaves for
the thunk, which runs the operation on the frame.

Generated code is capped at `BASELINE_CODE_CAP` (64 MiB) for the whole heap.
The cap is per function too: a function longer than `BASELINE_MAX_WORDS` (65536
bytecode words) is not compiled.

## Optimizing tier

`--jit` enables it on top of the baseline; `--no-opt` keeps only the baseline, and `--opt-no-inline`, `--opt-no-region` and `--opt-no-sink` switch off single optimizations. A function that reaches the hot
threshold is built into an SSA graph and given a second native body; the
baseline body stays, and an optimized body's exits continue in it.

What the graph holds: int32 and double arithmetic in machine registers, typed
loads, field reads and writes through shape guards, element access through the
same class guards the baseline uses, calls (with a callee guard and a branch per
target), and — inside inlined callees — their bodies spliced into the caller.
Allocation in an inlined constructor can be sunk: an object that only flows into
field stores and exits is built by the exit stub instead of at its allocation.

Anything else is a GENERIC node: the baseline emitter's code for that
instruction, run on the window after the dirty registers are stored.

The tier gives up in three ways, each counted by `--jit-stats`:

- a **refusal**: the function never gets a graph (kind, control flow graph
  opcode, graph size, register pressure, opcode, compile failure). The reason
  and the offending opcode are reported.
- an **exit**: optimized code leaves for the baseline body when a guard fails
  (shape, not-int32, not-number, bounds, hole, callee, slow path, overflow, cold
  feedback). The site records what it met, so the next build lowers it for that
  case instead of guarding again.
- a **discard**: a body that keeps exiting is thrown away and rebuilt without
  the sites that failed; a site that keeps failing is lowered generically (a
  BAN) and the body is rebuilt once more.

### Policy limits

| Limit | Value | Effect |
|---|---|---|
| `OPT_ENTRY_THRESHOLD` | 1000 | calls before an optimizing compile; each discard doubles the wait, up to 4x |
| `OPT_LOOP_CREDIT` | 250 | what one back edge adds to that count |
| `OPT_EXIT_MAX` | 8 | exits that discard a body (`--opt-exit-max`) |
| `OPT_REOPT_MAX` | 2 | discards before a function is left to the baseline |
| `OPT_BAN_MAX` | 16 | sites an exit can ban in one body before it is discarded outright |
| `OPT_CODE_MAX` | 4 MiB | optimized code kept in memory, least recently entered evicted (`--opt-code-max`) |
| `OPT_BLOCK_MAX` | 1024 | blocks in one graph |
| `OPT_STATE_MAX` | 256 KiB | blocks times registers, the build's per-block state |
| `INLINE_WORDS_MAX` | 64 | words in an inlined callee |
| `INLINE_TREE_WORDS_MAX` | 200 | words over the whole inline tree |
| `OPT_INLINE_DEPTH` | 3 | nested inline sites |
| `IC_POLY_MAX` | 5 | receiver shapes one field site compares |
| control flow graph | 4096 words | a longer function stays in the baseline tier |

A function's refusals, exits, bans and discards are counted per function, and
the record survives across compiles until the function is freed.

### Diagnostics

`--jit-stats` prints the baseline and optimizing counters at exit:
compile counts and time (total and longest, both tiers), live and peak
generated bytes, inline results, and per-reason tallies of refusals, exits,
field skips and generic lowerings. `--opt-log` traces each refusal, exit and
discard with the function and program counter; `--opt-dump` prints the graph.

## Testing

| Check | Command |
|---|---|
| Local suite, 5 modes | `bash scripts/jit_check.sh ./out/boomkat` |
| Forced exits, discard and ban paths | `bash scripts/opt_exit_check.sh` |
| Differential suites | `bash scripts/run_jit_diff.sh ./out/boomkat` |
| Differential test262 | `PATH=/usr/bin:/bin bash scripts/run_jit_diff.sh --test262 ./out/test262_runner` |
| Optimizing tier differential | `JIT_FLAGS="--opt-always --jit-stress" bash scripts/run_jit_diff.sh ./out/boomkat` |
| Embedding JIT suites | `make test-jit-api` and `make test-jit-api-asan` |
| Sanitized differential | `make test-jit-asan` |

`jit_check.sh` runs each fixture through the interpreter, the baseline tier,
the optimizing tier, the optimizing tier forced on, and the stress mode, and
reports any output that differs. The forced-exit script runs each fixture with
every exit reason forced, so the exit, materialization and discard paths run
even for code that never exits naturally.

The sanitized builds are `out/boomkat_jit_asan` (engine, same features as
`boomkat`), `out/test262_runner_jit_asan` (conformance runner) and
`out/jit_tiers_asan` (both tiers through the embedding API). They build at O2:
at O1 with threaded dispatch a run that allocates a few thousand objects
overflows its stack and dies without a report.

## Measured bounds

Apple M3, this branch, the full Octane suite in one process with
`--jit-stats`: 485 ms of compilation in total across both tiers, the
longest single compile 21 ms (a 37006-word baseline compile), 63.4 MB of
generated code live at exit (65.2 MB peak) and 2.4 MB of optimized code after
20 sweeps of the 4 MiB cap. Function compilation is 2089 optimizing compiles
for 610 discards and 97 refusals. These are properties of the suite and the
machine, not guarantees: the caps above are what bounds them.
